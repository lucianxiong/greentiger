# 长文本 / 长上下文（3.30.0）

目标：几百页文档、长代码文件、长会话进来时，绿虎不再「贴进来就被截成 24k」，
也不再「每轮改一点历史，把 prompt cache 全部打掉」。

参考的是 Claude 的四个做法：**长文放前面 + 先引用再回答**、**文档索引/分段读**、
**context editing**（超水位才批量清旧工具结果）、**compaction**（结构化交接摘要）。
当前通道是 OpenAI 兼容端点，Anthropic 的 `cache_control` 显式缓存标记在兼容层不被支持，
所以这里做的是「稳定前缀」——让 OpenAI / DeepSeek 一类自动前缀缓存能命中。

## 1. 预算跟窗口走（`ContextPolicy`）

以前这些数字是写死的：输入 24,000 字、工具结果 6,000+2,000、read_file 120,000、
历史 40 条、每条正文 12,000。1M 窗口的模型也只能用到 2%，等于白买长上下文。

| 模型窗口 | 单条输入 | 工具结果（头+尾） | read_file 单次 | 压缩水位 | 原生历史 |
|---|---|---|---|---|---|
| 32k（未知模型） | 15.7k 字 | 6k + 2k | 10k 字 | 23.6k 字 | 64 条 |
| 128k | 62.9k 字 | 10k + 3k | 15k 字 | 92.2k 字 | 96 条 |
| 200k | 96k 字 | 16k + 5k | 23k 字 | 144k 字 | 96 条 |
| 1M | 300k 字（封顶） | 24k + 8k | 34k 字 | 600k 字 | 120 条 |

文本围栏协议（无原生 tools、每次整段重发）单独收紧到 **32k 字输入 / 24 条历史**。
输入超预算时不再只砍尾巴：保留头 70% + 尾 30%，因为**用户的问题通常写在长文最后**。

## 2. 文档索引：先看地图，再读原文

`read_file` 新增 `outline: true`：

- Markdown：`#/##/###` 标题；
- 中文文档：`第一章` / `一、` / `1.1 节`；
- 代码：`class` / `def` / `function` / `public ...` 等符号；
- 只回 `L行号 + 标题`，不回正文；最多 240 条，超出提示用 grep 搜标题。

模型拿到索引后按 `offset/limit` 读需要的段。系统提示与长文任务里的 `[长文本任务]` 简报
都会强制这一步，避免「整读 400 页 → 头尾截断 → 中间全丢」。

## 3. 长文工作法（注入时机）

- 用户单条输入 ≥ 12,000 字，或附件里文档 ≥ 48 KB：在首条消息注入 `[长文本任务 · 长上下文工作法]`，
  四步：建索引 → 先引原句 → 分块笔记（事实/数字/引文/位置）→ 压缩后靠索引+已读段+笔记续接。
- 系统提示常驻一小节「长文本 / 长文档」，保证通过工具读到大文件时也遵守同一套纪律。
- 结论必须区分「原文明确写了」与「我的推断」。

## 4. Context editing：批量折叠，不每轮改写

`Brain.AppendToolResults` 以前每追加一条结果就 `AgeToolMessages`，旧消息前缀每轮都变，
自动 prompt cache 永远命中不了。现在：

1. 追加完整结果（按窗口预算截断头尾）；
2. 只有历史总字符超过 `ApiHistoryChars`（压缩水位的 80%）才触发一次批量折叠；
3. 一次折到水位的 70%，保留最近 12 条工具结果；
4. 两次编辑之间的请求前缀完全不变。

`TrimHistory` 删除了「每条 user / assistant 正文压到 6k/12k」的逻辑——长文档就在首条 user 消息里，
每轮重写它既毁缓存又毁内容。历史条数上限由窗口决定（64/96/120），丢旧轮次只在极长任务发生。

## 5. Compaction：结构化交接，不是流水账

`/compact` 与自动压缩的摘要提示改为固定小节：

```
## 任务目标与验收标准
## 已完成（每条带证据：文件路径 / 命令 / 结果）
## 关键决定与约束
## 未完成 / 下一步
## 文件与位置（长文档写已读/未读行段）
## 错误与死路（原文错误码/信息）
## 用户原话要点
```

取样也改了：最早的用户目标单独置顶（保留头 1200 + 尾 1000 字），最近 6 条消息每条约 4000 字，
更早的消息按 1200-1600 字，工具输出每条 500 字；总量受 `CompactTranscriptChars` 限制
（32k 窗口 16k 字、128k 39k 字、1M 180k 字）。摘要长度按窗口给 1200-3200 字。

## 6. 明确没做的

- **Anthropic 原生 Messages API + `cache_control`**：当前只有 OpenAI 兼容单通道；兼容层不支持 prompt caching，
  加未知字段有被判 400 的风险，没在没有 Key 的环境盲加。稳定前缀已能让自动缓存类端点受益。
- **PDF / 扫描件 OCR 直读**：`read_file` 只处理文本；PDF 先走 `pdf` 技能或外部转换，再进长文流程。
- **> 8 MB 单文件**：`read_file` 仍拒绝，需 shell 分段或先切分。
- **真实旗舰模型实测**：开发环境没有旗舰 Key，本轮只做了确定性单元/循环自检，没跑真实长文请求。

## 7. 验证

- `--self-test` 新增断言：预算随窗口放大、1M 压缩水位 600k、文本协议 32k、批量折叠保留最近结果、
  outline 识别 Markdown/中文章节/代码符号、长文简报只在长输入注入。
- `read_file outline` 与长文简报可通过真实文件手工复核：对一份 300 页 Markdown 先 `outline:true`，
  再按索引读两段，确认模型回答带 `文件:行号` 引文。
